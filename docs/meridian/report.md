## Architecture and guarantees

One Node/TypeScript process owns the Express API, one active Playwright run and a signed filesystem journal. Callers invoke named capabilities with typed arguments through `InvocationService`; deterministic replay executes reviewed artifacts. Discovery uses the same guarded surface to produce artifacts for review. The assistant-ui/Vercel AI SDK front end is a thin consumer of that API, with catalog, run history, outputs, status and evidence views. Integration is in [PR #84](https://github.com/goodwiins/computer-use-automation-system/pull/84), not yet merged or accepted end to end.

Credentials and operator roles stay server-side. Route/action restrictions, native token inspection, exact request/review matching and fresh eligibility checks run before posting. Human approval is specific to the inspected operation and expires; neither the model nor an API caller can grant it. A durable dispatch-intent transition precedes native posting. Failed or unverifiable completion after dispatch remains unknown without automatic retry. Public approval context retains visible transaction facts while masking credentials, hidden tokens and raw submission bodies. Evidence is redacted and caller-scoped.

The single-process limit keeps journal and browser ownership straightforward, at the cost of one active run and dependence on one host. Multi-worker scheduling is a future scaling decision. The canonical transfer result fields are an internal comparison contract; they do not prescribe six physical HTML columns. Grouped extraction can fit the observed UI, but actual receipt selectors and confirmation relationships must come from a genuine recording. Separate PRs and detailed validation gates make changes reviewable and add integration time; they are implementation choices, not extra assignment requirements.
